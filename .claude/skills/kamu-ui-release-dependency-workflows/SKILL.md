# Kamu UI Release And Dependency Workflows

Use this skill for release-scale work. Do not apply release steps to incremental local edits
unless the user explicitly asks for PR or release preparation.

section there step by step; this skill only adds what an agent must watch for. If the two

## Changelog

`CHANGELOG.md` follows Keep a Changelog with SemVer. This section owns its structure; how an
entry is worded is owned by `kamu-ui-prose-and-comments` ("CHANGELOG wording"), and when an entry
is added or reviewed by [AGENTS.md, "Changelog review context"](../../../AGENTS.md#changelog-review-context).

- Entries go under `## [Unreleased]`, in `### Added` for new features, `### Changed` for
  behaviour changes and `### Fixed` for bug fixes.
- One consolidated entry per user-visible change, never one per implementation step; nested
  bullets for the parts of one larger feature.
- Keep the literal `## [Unreleased]` heading: `update-changelog.js` finds that line during
  `npm version` and replaces it with `## [x.y.z] - YYYY-MM-DD`; without it the release fails.

## Release scripts

`npm run release-{patch,minor,major}` runs `npm version`, which bumps `package.json` and
`package-lock.json`, runs `update-changelog.js` (dates the changelog section, rewrites line 14 of
`LICENSE.txt` with the new version), commits `Release vX.Y.Z` and tags `vX.Y.Z`. Pushing the tag
triggers `.github/workflows/release.yaml`.

## Dependencies

- `npm ci` installs exactly the lock file; use it after switching branches. `npm install` with
  no arguments reconciles `package-lock.json` with `package.json`.
- Adding, removing or upgrading a package needs explicit user approval for that change
  (AGENTS.md, "Hard rules"); the command hook asks for it.
- Angular packages move together on the same major.minor: the framework (`@angular/core`,
  `@angular/common`, `@angular/compiler-cli` and the other `@angular/*` packages released with
  them), the build tooling (`@angular/cli`, `@angular/build`), and
  `@angular/cdk` with `@angular/material`. Patch versions differ between these three groups.
  Major Angular upgrades go through `ng update`, one major at a time; when handing back, tell the
  user which changes its automated migrations made and which were made by hand.
- Libraries that depend on Angular or on each other move with them, and a few are pinned — the
  list is [`update-dependecies.md`](../../../update-dependecies.md). Touch a pinned package only
  when the user asks.
- `package-lock.json` is regenerated by npm, never edited by hand (the edit hook refuses it).
- After any dependency change: `npm run lint`, `npm test`, `npm run build-prod` — the production
  build catches library incompatibilities the dev build does not. After a Material, CDK or
  Bootstrap upgrade, also `npm run check-styles`: it reports the classes and tokens our styles
  still name that the new version dropped.

## Agent checklist

- Every commit, tag and push in these procedures needs explicit user approval for that step
  (AGENTS.md, "Hard rules"). Prepare the change, report, and stop.
- `npm run release-*` commits and tags by itself; it needs the same approval as `git commit`.
- When deferring a hard upgrade, tell the user which package and why, so they can ticket it.
